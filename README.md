# Авито.Кухня — API заказов

Решение задания Авито Backend, осень 2026, для КТ2 «Примерка роли».

[Исходное задание](https://github.com/avito-tech/tech-internship/blob/main/Tech%20Internships/Backend/Backend-trainee-assignment-autumn-2026/Backend-trainee-assignment-autumn-2026.md)

## Реализованный сценарий

Клиент просматривает меню одного демо-кафе, оформляет заказ и получает его номер. Сотрудник кафе получает новые заказы через отдельный сервис и подтверждает выбранный заказ. Клиент видит статус `accepted`. Начальный статус — `pending`.

Основное API хранит данные в SQLite. Сервис кафе взаимодействует с ним по HTTP. В меню два доступных блюда и одно недоступное для проверки ошибок. Стоимость хранится в целых копейках и рассчитывается сервером. Название и цена блюда сохраняются в заказе. Создание заказа выполняется в транзакции, повторное подтверждение безопасно.

## Запуск на macOS в VS Code

Нужен Python 3.11 или новее. Открой эту папку через File → Open Folder, затем Terminal → New Terminal. Все команды ниже выполняются из корня проекта.

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-lock.txt
python -m uvicorn app.main:app --reload --port 8000
```

Оставь первый терминал работающим. Открой второй терминал VS Code в этой же папке.

```bash
source .venv/bin/activate
python -m uvicorn app.cafe:app --reload --port 8001
```

Открой в браузере http://127.0.0.1:8000/docs для основного API и http://127.0.0.1:8001/docs для кафе. Здесь можно выполнять запросы кнопками **Try it out → Execute**. Остановка сервиса — Ctrl+C в его терминале.

## Демонстрация через браузер

1. В документации основного API выполни `GET /menu`.
2. Выполни `POST /orders` с телом ниже.
3. Скопируй `id` из ответа. Цена заказа должна быть 70000 копеек, статус `pending`.
4. В документации кафе выполни `GET /orders`. В поле `x-cafe-token` введи `local-demo-token`.
5. Там же выполни `POST /orders/{order_id}/accept`, указав номер заказа и тот же токен.
6. В основном API выполни `GET /orders/{order_id}`. Статус должен быть `accepted`.

```json
{
  "customer_id": "demo-user",
  "address": "Пермь, улица Ленина, 1",
  "items": [{"dish_id": 1, "quantity": 2}]
}
```

`customer_id` — демонстрационный идентификатор клиента. Заказ получает случайный UUID. Ввод адреса обязателен, географическая проверка адреса за рамками реализации.

## Docker Compose

После установки и запуска Docker Desktop выполни в корне проекта следующую команду. Порты 8000 и 8001 должны быть свободны — останови локальные сервисы, если они запущены.

```bash
docker compose up --build
```

Адреса документации остаются теми же. Для остановки выполни `docker compose down`. База сохраняется в именованном томе `kitchen-data`. При локальном запуске база находится в `data/kitchen.db`.

Оба сервиса используют общий параметр `CAFE_TOKEN`. Значение по умолчанию `local-demo-token` предназначено для локальной демонстрации. В Compose его можно заменить через переменную окружения. Сервис кафе использует `API_URL` для адреса основного API. `DB_PATH` задаёт путь к базе основного сервиса.

## Структура проекта

- `app/main.py` — основное API, проверка данных и операции с базой.
- `app/cafe.py` — отдельный сервис кафе.
- `migrations/001_initial.sql` — создание таблиц, индекса и демонстрационного меню.
- `docs/openapi.json` и `docs/cafe-openapi.json` — спецификации API.
- `docs/architecture.puml` — C4-диаграмма контейнеров.
- `docs/customer-journey.puml` и `docs/cafe-journey.puml` — пути клиента и кафе.
- `tests/test_orders.py` — автоматические проверки.
- `requirements-lock.txt` — точные версии зависимостей проверенного окружения.

Диаграммы написаны на PlantUML. Для C4 используется стандартная библиотека C4-PlantUML. Их исходники доступны для просмотра и рендеринга инструментами PlantUML.

## Схема базы данных

`restaurants` хранит заведение. `dishes` связан с заведением через `restaurant_id` и хранит доступность и цену блюда. `orders` содержит клиента, адрес, статус, сумму и время создания. `order_items` связывает заказ с блюдами и сохраняет количество, название и цену на момент покупки.

Миграция автоматически применяется при старте и допускает повторный запуск. Внешние ключи включены. WAL и транзакция `BEGIN IMMEDIATE` обеспечивают согласованность записи при одновременных запросах в пределах SQLite.

## Проверка

```bash
python -m pytest -q
python -m ruff check app tests
```

Проверяются полный цикл заказа, доступ кафе по токену, повторное подтверждение, связь двух приложений через HTTP-клиент с тестовым транспортом, сохранение данных после повторного старта, неизвестный заказ, пустой список, нулевое количество, отсутствующее или недоступное блюдо, повторяющиеся позиции. При ошибке заказа проверяется отсутствие частично сохранённых данных.

При подготовке проекта прошли 10 тестов и проверка Ruff. Зависимость Starlette выводит предупреждение об устаревающем тестовом транспорте httpx. Запуск в Docker на момент подготовки не проверен, Docker Desktop отсутствует. Перед сдачей необходимо выполнить демонстрационный сценарий через Docker Compose и записать фактический результат в отчёт.

## Принятые ограничения

Для КТ2 выбран один сквозной сценарий одного кафе с заранее заполненным меню. Подключение новых заведений, редактирование меню, оплата, доставка и отмена заказа остаются за рамками выбранного объёма. Аутентификация покупателей и веб-интерфейс исключены исходным условием. Доступ к партнёрским операциям защищён демонстрационным токеном.

Покупатель передаёт собственный идентификатор, проверка его личности отсутствует. Подтверждение заказа выполняет сотрудник запросом к сервису кафе. Повторная отправка `POST /orders` создаёт новый заказ. При недоступности основного API сервис кафе возвращает 503. Решение предназначено для локальной учебной демонстрации.

## Использование ИИ

Начальная реализация, тесты, документация и диаграммы подготовлены с помощью ИИ по выбранному объёму КТ2. В отчёте следует отдельно указать, какие части были изучены, проверены и изменены автором работы, и записать фактически затраченное время.
